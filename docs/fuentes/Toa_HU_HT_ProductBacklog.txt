1. INTRODUCCIÓN
Este documento organiza los requisitos del proyecto en historias de usuario, historias técnicas y una pila del producto 
priorizada. Toma como documentos de referencia el anteproyecto de tesis, la especificación de requisitos IEEE 830 
(RF-01 a RF-18 y RNF-01 a RNF-06), los casos de uso preparados para el proyecto y los lineamientos de 
Aplicaciones Informáticas II. La estructura de fichas sigue el formato explicado en las diapositivas del docente y 
presentado en el ejercicio de referencia de la asignatura.
La aplicación se centra en tutorías académicas entre estudiantes universitarios: publicación y búsqueda por asignatura, 
horarios, coordinación, mensajería y administración. Se conservan la importación de horario desde PDF con 
confirmación manual, las recomendaciones por materia y coincidencia horaria y la cercanía opcional. Como 
ampliaciones propuestas, se incluyen conversación previa a la solicitud, oferta personalizada gratuita/remunerada y 
procesamiento de pagos. Estas ampliaciones no sustituyen los objetivos aprobados de la tesis ni se confunden con 
requisitos originales.
2. CONTEXTO, ROLES Y CONTROL DEL ALCANCE
2.1 Objetivos del anteproyecto (sin modificación)
Objetivo general: Desarrollar una aplicación web para gestionar tutorías académicas entre estudiantes universitarios.
Objetivos específicos (transcripción del anteproyecto):
1. Determinar los requerimientos funcionales y no funcionales de la aplicación web de tutorías académicas entre 
estudiantes universitarios, mediante técnicas de recolección de información y definición de historias de usuario.
2. Diseñar la arquitectura del sistema, las interfaces de usuario (UI/UX) y el modelo de datos relacional de la 
aplicación web de tutorías académicas, mediante el uso de diagramas UML, herramientas de prototipado y 
modelado entidad-relación.
3. Desarrollar los módulos de la aplicación, utilizando tecnologías web y un enfoque de desarrollo incremental.
4. Evaluar la eficiencia de desempeño de la aplicación web mediante pruebas basadas en la norma ISO/IEC 
25010:2023
2.2 Roles y módulos previstos
Rol Funciones principales
Estudiante solicitante Buscar tutores; comparar horarios; conversar; enviar solicitudes; valorar y aceptar 
propuestas; gestionar sesiones; pagar cuando corresponda.
Estudiante tutor Publicar ofertas académicas; definir disponibilidad; comunicarse; gestionar solicitudes; 
emitir propuestas gratuitas o remuneradas.
Administrador Gestionar información de usuarios, publicaciones y sesiones mediante acciones autorizadas.
Los cinco módulos del anteproyecto se mantienen: usuarios, tutorías, horarios, comunicación y gestión. La gestión de 
propuestas y pagos se documenta como ampliación funcional vinculada con tutorías, coordinación y sesiones; no 
representa un cambio del objetivo general.
2.3 Requisitos originales y ampliaciones propuestas
Los códigos RF-01 a RF-18 pertenecen a la ERS original y no se renombran. Los códigos RF-P01 a RF-P05 
identifican modificaciones funcionales propuestas para futura revisión formal de la ERS. No se atribuyen estos 
requisitos propuestos al documento original.

Regla propuesta para mantener coherencia: una tutoría gratuita puede confirmarse sin procesar un pago; una 
remunerada requiere una propuesta aceptada y verificación del proveedor antes de marcarla pagada. La coordinación

proveedor antes de poner en producción el cobro.
La plataforma no cobrará comisión propia en la primera versión. Ello no significa que el procesador sea gratuito. 
Cobrar comisiones, retener fondos directamente y funciones avanzadas de monetización se excluyen de este backlog; 
podrían evaluarse en una versión futura.
2.4 Tecnologías y criterios no funcionales
Arquitectura cliente-servidor de tres capas: presentación con React y Tailwind CSS; API REST con Node.js y 
Express; acceso a datos y persistencia PostgreSQL. El modelo relacional y los repositorios se representan como 
componentes de acceso a datos, en coherencia con el diagrama arquitectónico trabajado para la asignatura. La 
extracción de PDF y el motor de recomendación se resolverán inicialmente con reglas de procesamiento, sin requerir 
IA generativa.
Se conserva el RNF-01 original: en el entorno piloto, por lo menos 95 % de las operaciones habituales de consulta, 
registro y actualización deberán responder como máximo en 3 segundos; las recomendaciones podrán tomar hasta 5 
segundos. También se consideran RNF-02 (seguridad), RNF-03 (fiabilidad), RNF-04 (disponibilidad), RNF-05 
(mantenibilidad) y RNF-06 (portabilidad). La evaluación de eficiencia de desempeño deriva directamente del objetivo 
específico de tesis.
3. HISTORIAS DE USUARIO
3.1 Formato y convenciones
Cada historia expresa «Como [rol], quiero [funcionalidad], para [beneficio]» y contiene identificador, estimación, 
prioridad, dependencias, referencias de requisito y entre tres y cuatro criterios de aceptación verificables expresados 
con contexto, evento y resultado esperado. No especifica pasos de navegación ni herramientas de implementación. 
Los puntos de historia (serie 1, 2, 3, 5, 8, 13) son estimaciones preliminares de esfuerzo relativo, sujetas a revisión 
docente. La prioridad de una HU puede reajustarse al cambiar el alcance: por ejemplo, la mensajería RF-15 era de 
prioridad media en la ERS original, pero HU-14 se prioriza alta porque el contacto previo habilita el nuevo flujo 
propuesto de ofertas.

5. PILA DEL PRODUCTO (PRODUCT BACKLOG)
5.1 Criterios de ordenación
El Product Backlog integra todas las historias de usuario y técnicas en un único orden de ejecución. Prioridad indica 
la importancia del elemento; dependencia identifica lo que debe existir antes de implementarlo. La secuencia 
propuesta respeta esas dependencias y adelanta la investigación del proveedor de pagos para detectar riesgos antes de 
integrar cobros. Cada incremento corresponde a dos semanas dentro del plazo referencial de dieciséis semanas.
Este backlog no duplica el esfuerzo: cada HU y cada HT aparece una sola vez. Las HT habilitan funcionalidades pero 
no sustituyen las HU. La distribución temporal es una propuesta y debe reevaluarse si la velocidad de trabajo o la 
selección de la pasarela requieren más tiempo.
