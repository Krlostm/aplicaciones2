1 Introducción 
El presente documento contiene la Especificación de Requisitos de Software de una 
aplicación web para gestionar tutorías académicas entre estudiantes universitarios. Define 
de manera organizada las funciones que debe cumplir el sistema, sus interfaces, 
restricciones y requisitos de calidad, con el fin de servir como base para el diseño, 
desarrollo, pruebas y validación del producto. 
1.1 Propósito 
El propósito de este documento es establecer los requisitos funcionales y no funcionales  
de la aplicación web de tutorías académicas. Está dirigido al responsable del desarrollo, 
al docente de la asignatura y a los estudiantes que participen en la validación del 
sistema. 
1.2 Alcance 
El producto será una aplicación web que conectará a estudiantes que necesitan apoyo 
académico con estudiantes que ofrecen tutorías. Permitirá gestionar cuentas y perfiles, 
publicar tutorías, cargar o registrar horarios, administrar disponibilidad, buscar apoyo por 
asignatura, recomendar tutores considerando materia, coincidencia horaria y cercanía 
cuando el usuario autorice su ubicación, solicitar y coordinar sesiones, comunicarse 
entre participantes y administrar la información básica de la plataforma. La primera 
versión no incluirá pagos integrados ni videollamadas propias.

requisito no funcional. Tutor: estudiante que ofrece apoyo académico. Solicitante: 
estudiante que busca apoyo. Tutoría: sesión de apoyo académico entre estudiantes.

horario y, de forma opcional, cercanía. PDF: formato utilizado para cargar el horario

2 Descripción general 
2.1 Perspectiva del producto 
La aplicación será un producto web independiente, orientado inicialmente al entorno 
universitario. Funcionará con una arquitectura cliente-servidor: el usuario accederá 
desde un navegador, el frontend se desarrollará con React y Tailwind CSS, el backend 
utilizará Node.js y la información se almacenará en PostgreSQL. El sistema no 
reemplazará plataformas académicas institucionales; su finalidad será organizar tutorías 
entre pares. 
2.2 Funcionalidad del producto 
Las funciones principales serán: registro e inicio de sesión; gestión de perfiles; 
publicación de tutorías; carga del horario académico en PDF y confirmación de franjas 
detectadas; registro de disponibilidad; búsqueda de tutores por asignatura; 
recomendación por materia, horario y cercanía opcional; solicitud y gestión de tutorías; 
mensajería entre participantes; consulta de sesiones; y administración básica de 
usuarios y tutorías. 
2.3 Características de los usuarios 
Tipo de usuario Estudiante solicitante; estudiante tutor; administrador. 
Formación Estudiantes universitarios; administrador con conocimientos 
básicos de gestión del sistema. 
Habilidades Uso básico de aplicaciones web y navegación. El tutor debe 
conocer las asignaturas en las que ofrece apoyo. 
Actividades Buscar u ofrecer tutorías, registrar disponibilidad, coordinar 
sesiones, comunicarse y, en el caso del administrador, 
supervisar información de la plataforma. 
2.4 Restricciones 
El sistema se desarrollará como aplicación web y requerirá conexión a internet y un 
navegador moderno. El frontend utilizará React y Tailwind CSS, el backend Node.js y la 
base de datos PostgreSQL. La primera versión se desarrollará en 16 semanas. La 
ubicación será opcional. La lectura de horarios dependerá de la estructura y legibilidad 
del PDF, por lo que el usuario deberá poder confirmar o corregir la información 
detectada. No se procesarán pagos dentro de la primera versión. 
2.5 Suposiciones y dependencias 
Se asume que los usuarios dispondrán de internet y un navegador compatible, que los 
tutores mantendrán actualizadas sus asignaturas y horarios, y que las asignaturas 
estarán registradas en el sistema. La recomendación por cercanía dependerá de que el 
usuario autorice la ubicación o seleccione una zona. El sistema dependerá también de la 
disponibilidad del servicio de hosting y de la base de datos durante las pruebas y el 
piloto. 
2.6 Evolución previsible del sistema 
En futuras versiones podrán incorporarse pagos en línea, calificaciones y reput ación de 
tutores, seguimiento del progreso académico, tutorías grupales, recomendaciones 
basadas en historial de uso y una aplicación móvil. Estas funciones no forman parte de 
los requisitos obligatorios de la primera versión.

3 Requisitos específicos 
3.1 Requisitos comunes de los interfaces 
Las interfaces del sistema deberán permitir el intercambio de información entre el 
usuario, la aplicación web, los servicios del backend y la base de datos, manteniendo 
una interacción clara y consistente. 
3.1.1 Interfaces de usuario 
La interfaz deberá ser responsiva y comprensible. Incluirá formularios para 
registro e inicio de sesión, perfil, publicación de tutorías y disponibilidad; buscador 
por asignatura; resultados de tutores compatibles; detalle de horarios; solicitudes; 
sesiones y mensajería. Los mensajes de error deberán ser claros y mostrarse 
cerca de la acción correspondiente. 
3.1.2 Interfaces de hardware 
No se requiere hardware especializado. El sistema podrá utilizarse desde 
computador, tableta o teléfono con navegador y acceso a internet. La 
geolocalización del dispositivo será opcional y solo se utilizará con autorización 
del usuario. 
3.1.3 Interfaces de software 
React se utilizará para la interfaz web, Tailwind CSS para el diseño responsivo, 
Node.js para la lógica del backend y PostgreSQL para almacenar usuarios, 
asignaturas, tutorías, horarios, solicitudes, sesiones y mensajes. Se empleará un 
componente de procesamiento de PDF para intentar obtener los datos del horario 
académico, manteniendo siempre una opción de corrección manual. 
3.1.4 Interfaces de comunicación 
La comunicación entre frontend y backend se realizará mediante servicios web 
sobre HTTP/HTTPS y el intercambio de datos se realizará en formato JSON. En 
el entorno desplegado deberá utilizarse HTTPS. La conexión a internet será 
necesaria para autenticación, consultas, registro de información y mensajería.  
3.2 Requisitos funcionales 
Los siguientes requisitos describen las acciones principales que debe ejecutar el 
software al recibir información, procesarla y generar resultados.

3.3 Requisitos no funcionales 
3.3.1 Requisitos de rendimiento 
En condiciones normales del entorno piloto, al menos el 95% de las operaciones 
comunes de consulta, registro y actualización deberán responder en un máximo 
de 3 segundos. La generación de recomendaciones podrá tomar hasta 5 
segundos cuando deba comparar disponibilidad y cercanía. 
3.3.2 Seguridad 
Las contraseñas deberán almacenarse mediante técnicas de hash. El sistema 
deberá aplicar control de acceso según el rol del usuario, utilizar HTTPS en el 
entorno desplegado y solicitar consentimiento antes de utilizar la ubicación. No se 
mostrará públicamente información personal que no sea necesaria para coordinar 
una tutoría. 
3.3.3 Fiabilidad 
El sistema deberá validar la información antes de registrar o modificar usuarios, 
horarios, solicitudes y sesiones. Si ocurre un error, deberá informar al usuario y 
conservar los datos previamente confirmados. Se deberán evitar registros 
duplicados o estados incompatibles en una misma sesión.

3.3.4 Disponibilidad 
Durante las pruebas y el piloto, el servicio deberá estar disponible al menos el 
95% del tiempo previsto de uso, excluyendo periodos de mantenimiento 
programado. 
3.3.5 Mantenibilidad 
El sistema deberá organizarse de forma modular, separando interfaz, lógica de 
negocio y acceso a datos. Se utilizará control de versiones y se mantendrá 
documentación técnica para facilitar correcciones, mantenimiento y la 
incorporación de nuevas funcionalidades. 
3.3.6 Portabilidad 
La aplicación deberá ejecutarse desde un navegador moderno sin instalación 
local y adaptar su interfaz a computadoras y dispositivos móviles. Se verificará su 
funcionamiento al menos en navegadores basados en Chromium y Firefox. 
3.4 Otros requisitos 
La plataforma deberá respetar la privacidad de los usuarios y solicitar únicamente la 
información necesaria. La ubicación será voluntaria. La lectura automática del horario en 
PDF deberá incluir una alternativa de confirmación o registro manual. La navegación 
deberá ser comprensible para usuarios sin conocimientos técnicos.
